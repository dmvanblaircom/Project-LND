# Suite's edge API (decision 0030)

Our own small API on Cloudflare Workers. Suite calls it; it holds provider
keys server-side, fetches, caches, and returns only what a screen shows.

- Code: `worker/src/index.js` (no dependencies). Checks:
  `node tools/workercheck.mjs` (in CI).
- Deploy: `.github/workflows/worker.yml`, on every change to `worker/` (or
  to the registry) on main, or from the Actions tab. Until the secrets below exist it stops
  green with a notice.
- Routes: `GET /v1/health`; `GET /v1/cfbd/sp?year=` and `GET /v1/cfbd/sp/week?year=&id=` (SP+, below); `GET /v1/cfbd/season?team=&year=` (CFBD season
  stats for one team, only the fields in `CFBD_FIELDS`: `games`,
  `rushingYardsOpponent`, `netPassingYardsOpponent`, for W15's yards
  allowed. The names come from a real response, read with *Probe CFBD
  field names* on 2026-10-01.) It answers only for a school in the
  registry, by the name the app sends, and only for this season or last;
  anything else is refused before CFBD is asked (404 / 400), so no script
  can spend the key's monthly allowance on made-up names (bug hunt,
  2026-10-02). FCS opponents are not in the registry: their yards-allowed
  rows show a dash. The list, `worker/src/schools.js`, is generated by
  `tools/build-worker-schools.js`, which the registry's workflow and the
  deploy both run.
- Game alerts (W19, `worker/src/push.js`): `GET /v1/push/key` (the VAPID
  public key), `POST /v1/push/subscribe` and `POST /v1/push/unsubscribe`
  (only from Suite's origin), and `GET /v1/push/status` (counts, watched
  games, events sent, the last minute's log; nothing about any fan). A cron
  every minute checks the followed teams'
  games and sends each follower the alerts they chose, once each, by Web
  Push. A subscription carries its `options` (round 2, notifications brief
  §2b: kickoff, final, delays, scoring off / my team / every score, end of
  each quarter, halftime, close finish and overtime); one made before them
  gets kickoff, final and delays. While a game is on, its score is read
  each minute; see the comment at the top of `push.js` for the rules (a
  score held a minute, extra points folded in, corrections, late alerts
  dropped, one lock-screen card per game). Storage is one Durable
  Object with SQLite (`Alerts`, created by the deploy's migration). The VAPID
  key pair is made on first use and kept there, unless a
  `VAPID_PRIVATE_JWK` Worker secret is set.
- Only Suite's origin (`https://dmvanblaircom.github.io`) may read it from
  a browser. Responses carry `fetchedAt`; a cached copy served because the
  provider failed carries `stale: true`.

## One-time setup (David, about 15 minutes)

1. **Cloudflare account** (free): sign up at dash.cloudflare.com. Open
   *Workers & Pages* once; if it asks you to choose a `workers.dev`
   subdomain, pick one (for example `suite`).
2. **Account ID:** shown on the *Workers & Pages* overview page. Copy it.
3. **API token:** profile menu → *My Profile* → *API Tokens* → *Create
   Token* → template **Edit Cloudflare Workers** → limit it to your account
   → create. Copy it (Cloudflare shows it once).
4. **CFBD API key** (free): request one at collegefootballdata.com; it
   arrives by email.
5. **GitHub secrets:** repository → *Settings* → *Secrets and variables* →
   *Actions* → *New repository secret*, three times:

   | Name | Value |
   | --- | --- |
   | `CLOUDFLARE_API_TOKEN` | the token from step 3 |
   | `CLOUDFLARE_ACCOUNT_ID` | the ID from step 2 |
   | `CFBD_API_KEY` | the key from step 4 |
   | `REFRESH_CLOCK_TOKEN` | the refresh clock's token (`data-refresh-clock.md`) |

6. Tell Claude. Claude runs *Deploy the edge API* and *Probe CFBD field
   names* and checks both.

None of these values ever goes in the repository.

## After setup

- **Is it up?** `https://suite-api.<your-subdomain>.workers.dev/v1/health`
  answers `{"ok":true,...}`; the deploy workflow checks this itself.
- **Rotating a key:** replace the GitHub secret and re-run *Deploy the
  edge API*.
- **The refresh clock** runs on this Worker (`docs/engineering/data-refresh-clock.md`).
- **Game alerts** (W19) run on this Worker. Kalshi stays on GitHub Actions.

## SP+ (`GET /v1/cfbd/sp?year=`, 2026-10-14)

Bill's permission (Oct 1): the SP+ top 25 with ranks and ratings, credited
to SP+ and CFBD (`rankings-sources.md`). The route answers exactly that:
`{ source: "cfbd-sp", year, fetchedAt, ranks: [{ rank, team, id, rating }] }`,
the rows ranked 25 or better (a tie can add a row). Nothing else of CFBD's
table leaves the Worker.

- **Identity.** CFBD's SP+ rows name a school and carry no id. The Worker
  joins each school, by exact name, to CFBD's `/teams/fbs` list, whose ids
  are ESPN's. *Probe CFBD SP+* (`tools/cfbd_sp_probe.py`, 2026-10-14, names
  and counts only) found all 138 registry programs under the same id and
  name, and all 25 top-25 schools in the list. A school it cannot place
  keeps `id: null`. The app accepts an id only when the registry lists it
  under the same name (`TeamOS.ratings.spPlus`).
- **Time.** CFBD publishes no edition time, so the answer has none:
  `fetchedAt` is when the Worker read it. There is no change history, so
  the screen has no Change column.
- **Cache and failure.** SP+ is fresh for 12 hours and the FBS list for a
  week (kept 60 days). When CFBD fails, or sends a table that is not a
  whole top 25, the last whole table is served with `stale: true`. With
  nothing saved, the answer is 502. An empty list from CFBD means "not
  published for that season" and is answered as `ranks: []`.
- **Allowance.** About two CFBD calls a day for SP+, plus one a week for
  the FBS list.
- **Weeks kept (David, 2026-10-21).** CFBD publishes only the current
  table, so earlier weeks exist only if they are kept as they appear. They
  are kept in the Worker's own Durable Object (`Ratings`, `src/sp.js`,
  binding `RATINGS`, migration `v2`), never as a file in the repository:
  CFBD's condition is that its data is shown, not published as reusable
  JSON (decision 0012). Each kept table holds the same four fields per row.
  - An edition is a table that differs from the last one read. It is
    filed under the football week ESPN's scoreboard names when it is first
    seen (`pre`, `wN`, `final`). A different table later the same day
    corrects that day's edition. A second edition in one ESPN week is kept
    as `wN-YYYY-MM-DD`. If ESPN cannot say the week, the table waits and is
    filed on a later read. Nothing kept is replaced by a later week; at
    most 40 editions a season.
  - `GET /v1/cfbd/sp` adds `week` (the edition this table is, or `null`
    until filed) and `weeks` (`[{ id, label, seen }]`, oldest first, no
    tables). A store that cannot answer leaves both off; the table stands.
  - `GET /v1/cfbd/sp/week?year=&id=` answers one kept edition:
    `{ source, year, fetchedAt (when first seen), week, label, ranks }`.
    404 for a week not kept, 400 for a malformed id or another season, 503
    with no store.
  - The half-hourly clock reads SP+ through the route itself when no table
    has been kept for 12 hours, so a week is kept even if no fan opens SP+.
    In January it keeps last season's final table.
- Tested by `tools/workercheck.mjs` (SP+ sections). Checked after every
  deploy by the *SP+ answers through it* step in `worker.yml`, which prints
  counts, key names and week ids only.
